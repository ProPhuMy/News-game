## Create a separate Render web service

The existing `render.yaml` describes `news-town` and is not staging-specific. Its Docker, instance, health-check, and AI-disabled settings are suitable starting values. Create a separate service manually to give staging its own name and branch without changing the existing blueprint or linking a production service to this phase branch. Manual service creation does not automatically apply `render.yaml`; enter all settings below.

In the Render dashboard, select **New > Web Service**, connect GitHub, and select `ProPhuMy/News-game`.

| Setting | Value |
| --- | --- |
| Name | `news-town-staging` or an available distinct staging name |
| Branch | `codex/visual-d0-5`, after publishing it |
| Language/runtime | Docker |
| Root directory | Leave empty (repository root) |
| Dockerfile path | `./Dockerfile` |
| Docker build context | Repository root (`.`) |
| Docker command override | Leave empty; use the existing Dockerfile CMD |
| Instance | Always-on paid compute, matching the blueprint's `0.5c-512mb` (0.5 CPU, 512 MB), or larger |
| Instance count | 1; do not enable autoscaling |
| Health check | `/` |
| Auto-deploy | Off |
| Persistent disks/databases | None required by the current application |
| `AI_PROVIDER` | `none` |
| `TRUST_RENDER_PROXY` | `true` for this Render-managed public service only |
| `NODE_ENV` | `production` (already set by Dockerfile; retain it) |

Review the displayed compute charge before clicking Create Web Service. Free compute sleeps on idle and does not meet the game's always-on hosting requirement. Do not create a static site: the same Node service hosts HTTP and Socket.IO.

## Rollback

Rollback is documented, not executed. Before replacing a working staging deployment, record its successful deploy ID and SHA. In **Deploys**, choose that successful deployment, select **Rollback**, confirm the target, and keep automatic deploys off. If its build artifact is unavailable, use **Manual Deploy > Deploy a specific commit** with the recorded known-good SHA and wait for a healthy rebuild. Verify the resulting SHA, environment values, instance count, HTTP assets, and WebSocket reconnect again.

There is no previous successful staging deployment for this first creation. Do not invent a rollback target; record the first verified deployment as the baseline for the next deployment. If the first deployment fails, inspect its logs and leave the D0.5 gate open.

Rooms live in process memory. A deploy, restart, or rollback interrupts active matches and cannot recover their state. Use a quiet staging window. A persistent disk does not make the current in-memory room manager durable. This phase introduces no persistence or multi-instance routing.
